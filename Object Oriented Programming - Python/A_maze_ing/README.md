# A-Maze-ing

A terminal-based maze generator written in Python as part of the 42 curriculum.

The project reads a maze configuration, validates the requested parameters, generates a maze using a randomized depth-first search, computes a shortest path with breadth-first search, renders the maze in the terminal, and exports the result using the hexadecimal format required by the activity.

## Description

A-Maze-ing is designed around a grid of cells. Every cell keeps its four cardinal walls and its position in the maze. The generator starts from a fully closed grid and removes shared walls while exploring neighbouring cells.

Two generation modes are supported through the `PERFECT` setting:

- `PERFECT=True` keepsF the maze as a perfect maze generated by the depth-first search/backtracking algorithm.
- `PERFECT=False` opens additional passages after the initial generation in order to introduce alternative routes and loops for a Pac-Man-like board.

The terminal renderer also provides interaction during execution: the user can regenerate a maze, show or hide the shortest path, change the wall-color palette, or quit.

The source code is divided into modules so that maze cells, grid management, generation, parsing, path finding, rendering, and colors are kept separate.

## Configuration

The program expects a configuration file containing one `KEY=VALUE` pair per line.

Lines beginning with `#` are ignored.

### Required configuration

```text
WIDTH=20
HEIGHT=20
ENTRY=0,0
EXIT=19,19
OUTPUT_FILE=maze.txt
PERFECT=False
```

### Optional seed

A `SEED` value can be supplied to make the generated maze reproducible:

```text
SEED=30
```

When a seed is provided, the same maze-generation parameters and the same seed produce the same random choices.

### Complete example

```text
# Maze dimensions
WIDTH=20
HEIGHT=20

# Entry and exit coordinates
ENTRY=0,0
EXIT=19,19

# Reproducible generation
SEED=30

# Output filename
OUTPUT_FILE=maze.txt

# Generation mode
PERFECT=False
```

### Configuration validation

The parser validates the configuration before maze generation. It checks, among other things:

- required variables are present;
- unknown variables are rejected;
- duplicate variables are rejected;
- each non-empty configuration line has exactly one `=`;
- width and height are numeric and positive;
- entry and exit contain two numeric coordinates;
- entry and exit are different and inside the maze;
- `PERFECT` accepts only `True` or `False`;
- the seed is numeric and non-negative;
- the output filename is not empty;
- parameters that cannot produce the requested mode are rejected;
- the terminal is large enough for the requested maze display.

Configuration errors are reported to the user instead of being allowed to fail later inside the maze algorithms.

## Maze Generation

### Algorithm: randomized Depth-First Search

The main generator uses an iterative **Depth-First Search (DFS)** / **recursive-backtracker** approach.

The algorithm keeps a stack of cells:

1. Start from the first cell.
2. Mark the current cell as visited.
3. Find an unvisited neighbouring cell.
4. Remove the shared wall between the current cell and that neighbour.
5. Move to the neighbour and continue.
6. When no unvisited neighbour is available, backtrack by removing the current cell from the stack.
7. Continue until the maze has been explored.

The implementation uses an explicit Python list as the stack instead of recursive function calls.

### Why this algorithm?

DFS/backtracking was chosen because it fits the cell-and-grid representation naturally and produces a perfect maze without requiring a complicated data structure. Using a dedicated seeded random generator also makes the traversal reproducible, which is required by the subject.

### Non-perfect mode

When `PERFECT=False`, the project performs a second pass over the generated maze and removes additional walls when the local structure allows it. This creates alternative routes rather than leaving the maze as a single-path tree.

The implementation keeps shared walls synchronized: when a wall is removed from one cell, the corresponding wall of the neighbouring cell is removed as well.

## Maze Rules

The generator represents the maze using four cardinal walls per cell:

```text
North
East
South
West
```

The generated maze is expected to satisfy the activity rules, including:

- entry and exit exist, are different, and are inside the maze;
- connected cells do not become isolated during normal generation;
- outer borders remain closed;
- neighbouring cells agree on every shared wall;
- no 3x3 completely open area is created;
- the `42` pattern is represented by closed cells when the maze is large enough;
- `PERFECT=True` produces a perfect maze with one path between reachable cells;
- `PERFECT=False` provides additional independent routes suitable for a Pac-Man-like board.

For a maze that is too small to contain the `42` pattern, the project reports an error rather than silently pretending that the pattern exists.

## The 42 Pattern

The generator reserves a set of cells around the centre of the board to form the visual `42` pattern when the maze is large enough.

Those cells are tracked separately so that normal generation and later passage-opening logic do not treat the pattern as ordinary corridor cells.

## Shortest Path

The project uses **Breadth-First Search (BFS)** to find a shortest path from the entry cell to the exit cell.

Because each movement between adjacent cells has the same cost, BFS explores the maze layer by layer and returns a shortest route once the destination is reached.

The resulting ordered cell path is converted into the four directions required by the output format:

```text
N E S W
```

For example:

```text
(0,0) -> (0,1) -> (0,2) -> (1,2)
```

becomes:

```text
EES
```

## Hexadecimal Output

The maze is exported using one hexadecimal digit per cell.

Each digit stores the state of the four walls as four bits:

| Bit | Direction |
|---:|---|
| 0 | North |
| 1 | East |
| 2 | South |
| 3 | West |

A closed wall is encoded as `1` and an open passage as `0`.

For example:

```text
3 = 0011
A = 1010
```

Cells are written row by row, with one maze row per line.

After an empty line, the output contains:

1. the entry coordinates;
2. the exit coordinates;
3. the shortest path using `N`, `E`, `S`, `W`.

Example shape:

```text
BD13
C3AA
96EA
C556

0,0
2,2
SESWSEEENNNWSS
```

The output format follows the activity specification, including the hexadecimal wall encoding and the three lines written after the empty line.

## Terminal Visualization

The project uses terminal ASCII rendering rather than MiniLibX.

The renderer displays:

- maze walls;
- entry cell;
- exit cell;
- the `42` pattern;
- the shortest path when enabled;
- colored walls.

### Interactive controls

```text
1. Re-generate a new maze
2. Show/Hide path from entry to exit
3. Rotate maze colors
4. Quit
```

The shortest path can be toggled while the same maze is displayed, and the wall-color palette can be rotated without changing the maze structure.

### Module responsibilities

#### `src/a_maze_ing.py`

Application entry point. It loads the configuration, initializes the grid, creates the `42` pattern, generates the maze, computes the solution, launches the interactive menu, and starts output generation.

#### `src/parsing.py`

Reads the configuration file and validates its syntax and values before generation starts.

#### `src/mazegen/cell.py`

Defines the `Cell` object, including its four wall states, position, visitation state, parent relationship, and hexadecimal encoding.

#### `src/mazegen/grid.py`

Owns the maze grid and the operations used by the generator and path finder, including neighbour selection, wall removal, wall consistency checks, and path state.

#### `src/mazegen/generator.py`

Contains the DFS generator, the additional passage-opening logic used by non-perfect mode, and the `42` pattern initialization.

#### `src/shortest_path.py`

Contains BFS path finding and conversion of a cell path into the required directional string.

#### `src/printer.py`

Handles terminal rendering and hexadecimal maze output.

#### `src/colors.py`

Defines ANSI color sequences and the available terminal color palettes.

## Reusable Maze Generator

A major requirement of the activity is code reusability. The maze-generation code is separated under the `mazegen` module so that it is not tied directly to the terminal menu or output formatting.

The reusable layer currently contains:

- `Cell` for the maze-cell representation;
- `Grid` for the generated maze structure and maze operations;
- generation functions for DFS, additional openings, and the `42` pattern.

### Subject requirement to complete before final submission

The activity specification requires the reusable generator to be exposed through a **unique generator class** (for example `MazeGenerator`) inside a standalone importable module, with documentation explaining how to:

- instantiate the generator;
- pass custom dimensions and a seed;
- access the generated maze structure;
- access a solution/path;
- build and install a `mazegen-*` package from the repository.

The current source is modular but still uses `Grid` plus generation functions rather than a dedicated `MazeGenerator` public API. This is therefore a final implementation task, not something the README should pretend has already been completed.

The repository will also include the required packaging files and a reusable package artifact named according to the `mazegen-*` convention.

## Project Management

The implementation evolved incrementally from a single-file maze program into a modular project.

The development path was approximately:

1. Start from the working maze implementation.
2. Split the original file into dedicated modules.
3. Separate maze generation, grid logic, path finding, rendering, colors, and parsing.
4. Fix output-file handling and move output configuration into the project state.
5. Add documentation and improve flake8 compatibility.
6. Add and refine the Makefile workflow.
7. Address mypy and package-structure issues.
8. Improve configuration validation and edge-case handling.
9. Keep the terminal visualization while adding path toggling and color rotation.
10. Prepare the reusable generator and packaging requirements for the final submission.

### What worked well

- Splitting the original implementation made the code easier to navigate and debug.
- The two-branch Git workflow allowed the team to work in parallel.
- Keeping DFS, BFS, parsing, and rendering in separate modules reduced coupling.
- Seeded random generation made maze behavior reproducible while debugging.
- Incremental refactoring helped preserve the existing terminal rendering while new functionality was added.

### What could be improved

- The final public API for the reusable generator should have been designed earlier.
- Automated tests should cover configuration, wall consistency, connectivity, output encoding, and generation modes from the beginning.
- Packaging should be treated as part of the initial architecture instead of a final step.
- The Makefile targets should always be verified against the final repository paths before submission.
